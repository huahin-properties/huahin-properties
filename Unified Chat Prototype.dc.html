Design Decision

Design Inspiration: Intercom/Front-style inbox shell, re-skinned per role (neutral/warm/professional) while keeping one structural layout.

Why This Design: One component reused across Customer/Member/Admin — same bubble system, same input, same states — with only the sidebar visibility and accent color changing per context. Bugs get fixed once; roles stay instantly recognizable by color during testing.

Why Not Separate UI Designs: Divergent chat UIs per role would drift over time and tempt building permission logic into the UI layer instead of the backend query/security layer — the actual place data isolation must live.

Trade-offs: Less per-role visual freedom in exchange for one shared, auditable design surface.

Expected Business Outcome: instant role recognition while testing, clear 1:1 lead ownership per conversation, no risk of cross-customer visibility, consistent training/onboarding.

Data Model & Security Proposal (ยังไม่ implement)
conversations/{conversationId}
  customerId, memberId, aiThreadEnabled, humanThreadEnabled
  source, collectionId, propertyIds[], projectId
  status, unreadByMember, unreadByCustomer, createdAt, updatedAt, lastMessageAt

messages/{messageId}
  conversationId, senderType:"customer"|"member"|"admin"|"ai"
  senderId, text, propertyContext, createdAt, readAt, moderationStatus

adminAccessLog/{logId}
  adminId, conversationId, reason, timestamp, action
  • Rules: exactly one customerId + one memberId per conversation — never a 3rd participant added to an existing thread
  • Member reads/writes only where memberId == auth.uid; Customer A cannot query Customer B's conversation even though both talk to the same member
  • Admin Inbox query spans all conversations by role permission — Member Inbox query is always scoped to memberId == auth.uid, never platform-wide
  • Any admin read of a private conversation is written to adminAccessLog
